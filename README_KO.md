# 코레일 공식 웹페이지 감시 v4 — 목포 출발 첫 화면 (Railway + Telegram)

이 프로그램은 **로그인 없이 열차 예약 가능 상태를 읽고 텔레그램 알림만 보내는 읽기 전용** 감시봇입니다. 자동 예약·좌석 선택·결제·인증/대기열 우회 기능은 없습니다.

## 1. 감시 조건

| 설정 | 값 |
|---|---|
| 검색일 | **2026-10-24 (토)** |
| 출발역 | **목포** |
| 기준 도착역 | **서울**, `인접역 보기` + `서울·용산-수서 함께 보기` 체크 |
| 승객 | 1명 |
| 열차 | **KTX/KTX-산천 필터**, 첫 화면에 표시되는 최대 10개 |
| 알림 | 일반실·특실에 **실제 운임(예: 46,800원) 표시**, 또는 **예약대기** 표시 |
| 제외 | `입석 + 좌석`, 입석/자유석, 매진, **456편(목포 11:43→서울)** |
| 조회 | 기본 **20~30초 랜덤**. 매 주기 브라우저 `F5`와 같은 새로고침 |
| 종료 | **2026-10-25 00:00 KST** (10/24 자정 직후) |

`더보기`를 누르지 않으며, 목포→서울·용산·수서를 **각각 3번 직접 호출하지 않습니다**. 코레일 사이트가 브라우저에서 목록을 갱신할 때 사용하는 요청은 여전히 발생합니다. **F5가 코레일 원본에 몇 번 요청하는지는 공개 규칙이 아니라 실제 배포 로그로 확인해야 합니다.**

현재 파일은 사용자가 보내준 **2026-10-24 검색 결과의 렌더링된 HTML**을 직접 분석하여 좌석 상태 추출 로직을 만들었습니다. `li.tckList`, `.flag_wrap .num`, `.data_box h3`, `.price_box`를 사용합니다.

### 테스트에서 확인된 내용

- 사용자 제공 HTML에서 KTX **10편** 판독, 17칸 `매진`, 3칸 `입석 + 좌석` → **잘못된 가용 알림 0건**.
- 모의 HTML에서 `46,800원` 및 `예약대기` 감지, `입석+좌석` 제외, 456편 제외, 날짜/출발역/필터 오류 차단.
- Python 구문 검사 및 로컬 단위 테스트 통과.
- **아직 검증되지 않은 부분:** Railway의 새로운 Chromium 브라우저가 최초 접속 시 날짜·역을 자동 선택할 수 있는지, 20~30초 새로고침에서 코레일이 접근을 허용하는지, 실제 예약대기/가격 화면 구조가 모의 케이스와 동일한지.

이 프로그램을 **바로 상용 수준으로 정상 동작한다고 가정하면 안 됩니다**. 반드시 초기 Railway 로그로 실환경 테스트해야 합니다.

## 2. Railway 배포

1. 이 ZIP의 압축을 풀고 **파일들 자체를** GitHub의 새 **Private Repository 최상위**에 올립니다. (ZIP 파일 하나만 올리면 안 됨.)
2. Railway → **New Project → Deploy from GitHub Repo**에서 해당 Repository 연결.
3. `Variables`에 아래 값 입력. 기존 텔레그램 봇의 토큰과 Chat ID를 그대로 재사용 가능.

| 변수 | 필수? | 값 / 기본값 |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | 필수 | 기존 텔레그램 봇 토큰 |
| `TELEGRAM_CHAT_ID` | 필수 | 본인 채팅 ID |
| `POLL_MIN_SECONDS` | 선택 | 기본 `20` |
| `POLL_MAX_SECONDS` | 선택 | 기본 `30` |
| `REFRESH_MODE` | 선택 | `reload` (F5 방식, 기본). `button` (검색 버튼으로 갱신; 문제가 생길 경우만 사용) |
| `HEARTBEAT_MINUTES` | 선택 | 기본 `60`, 0이면 정기 알림 해제 |
| `STATE_FILE` | 선택 | 기본 `korail_web_v4_state.json` |

4. Deploy Logs를 봅니다. 정상적인 시작 예시(실제 성공을 보장하는 로그가 아니라 **예시**입니다):

```text
코레일 웹 감시 v4-browser-firstpage 시작 ...
브라우저 최초 검색 검증 성공
#1 검증성공 KTX=10 일정API요청=1 | 404 05:23→서울 일반:SOLD_OUT ...
#2 검증성공 KTX=10 일정API요청=1 | ...
```

열차가 하나라도 가용이면 **첫 정상 스캔에서도 알림을 보냅니다.** 이후 같은 열차·객실의 동일 상태는 반복 알리지 않고, 매진된 뒤 다시 열리거나 `예약대기`로 바뀌면 다시 알립니다.

## 3. 반드시 알아둘 첫 배포 리스크

현재 사용자 PC에서는 검색 조건을 설정하고 `F5`를 누르면 열차 목록이 유지되지만, **Railway의 새 브라우저에는 PC의 기존 페이지/세션이 없습니다**. 따라서 v4는 자동으로 다음을 시도합니다.

1. `/ticket/search/list`로 들어가 이미 조건이 맞는지 확인.
2. 아니라면 `/ticket/search/general`에서 `목포→서울`, `10/24`, 1명, 통합검색 2개 체크를 설정하고 `열차조회`를 실행.
3. `KTX` 필터 선택 후 **조회 날짜·역·인원·필터를 모두 검증**.
4. 검증에 성공할 때만 예약 상태 판별 시작.

**첫 설정 화면의 달력·역 선택 팝업 실제 HTML은 사용자 제공 자료에 포함되지 않았습니다.** 따라서 자동 검색 설정이 실패할 수 있습니다. 이 경우 실패 이유를 Railway 로그로 명확히 남기며, 3번 연속 실패하면 텔레그램 경고 후 중단합니다. 오류 화면을 `매진`으로 잘못 취급하지 않습니다. **현재까지 검증된 것은 기존 검색결과 화면의 DOM 추출 로직이지, 새 Railway 세션에서의 첫 검색 동작까지가 아닙니다.**

첫 배포 후 `브라우저 최초 검색 검증 성공`이 나타나지 않거나 `검색 조건 자동 설정 실패`가 나타난다면 로그를 보내주세요. 어떤 입력/달력/역 선택 단계가 다른지 보고 다음 버전에서 수정할 수 있습니다. 이미 사용자의 검색결과 HTML은 확보했으므로 다시 복사할 필요 없습니다.

## 4. 차단/오류 대응

- HTTP **403/429**, 명백한 CAPTCHA·접근 제한·NetFunnel 대기화면 등 발생 시 **5분 → 10분** 대기. **3회 연속이면 자동 중단**, 텔레그램 알림. 인증이나 보안 제한은 우회하지 않습니다.
- HTML 구조 변화, 잘못된 날짜/역, 열차 목록 0건, 필터 해제 등은 **검증 실패**로 처리합니다. 예약 가능 알림을 보내지 않고 백오프 후 재시도합니다.
- 일반 오류: 60초 → 120초 → 240초 → 480초 → 최대 15분 대기. 3회 연속 실패면 텔레그램 경고 + 브라우저 재시작 시도.
- 최초 검색 조건 자동 설정 3회 실패 시 **중단**. 비정상인 채로 계속 20초마다 조회하지 않습니다.
- 정기 정상 작동 알림은 기본 **1시간**에 한 번.
- 자동 종료 후 Railway 프로세스가 재시작돼도 대상 날짜가 이미 지났으면 즉시 종료.

**주의:** 20~30초의 전체 새로고침은 코레일에 상당히 잦은 접근일 수 있습니다. 허용 한도를 알 수 없고 차단 위험이 있습니다. 필요하면 `POLL_MIN_SECONDS=60`, `POLL_MAX_SECONDS=90`부터 시험하세요. 여러 IP/계정으로 제한을 우회하지 않습니다.

## 5. 상태 유지

기본 저장 파일은 Railway 컨테이너 내부에 만들어지므로 재배포하면 사라질 수 있습니다. 중복 알림 방지가 중요하면 Railway Volume을 `/data`에 마운트하고 `STATE_FILE=/data/korail_web_v4_state.json`으로 설정하세요. Railway replica는 1개만 실행하세요.

## 6. 수동 오프라인 테스트

```bash
pip install -r requirements.txt
python -m unittest discover -s tests -v
```

테스트는 코레일 서버를 조회하지 않습니다.
